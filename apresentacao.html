Uma distinção importante

Quem produz o HTML? E quem interage?

CSR

No navegador

JavaScript monta e atualiza a interface do lado do cliente.

Bom para painéis altamente interativos.

SSR

No servidor

O servidor gera HTML para a requisição, útil quando a resposta depende de dados atualizados.

Ex.: página personalizada.

Server Components

Menos JS no cliente

Componentes executados no servidor podem obter dados sem enviar seu código ao navegador.

Interações usam fronteiras com "use client".

SSR, CSR e Server Components não são sinônimos nem opções mutuamente exclusivas em toda a aplicação.

Padrão 01 · Composite

Uma interface feita de peças reutilizáveis.

Da tela inteira ao item

TaskBoard organiza a área principal; TaskList percorre os dados; TaskCard apresenta uma tarefa.

TaskBoard → TaskList → TaskCard

Na vida real: o mesmo componente Card pode aparecer em uma vitrine, uma lista de desejos e recomendações.

TaskBoard.tsx · trecho real
function TaskList({ tasks }) {
  return <ul>{tasks.map(task =>
    <TaskCard
      key={task.id}
      task={task}
    />
  )}</ul>;
}

Benefício: componentes menores são mais fáceis de testar, reorganizar e reutilizar.

Padrão 02 · Observer

O estado muda. A tela acompanha.

O clique é só o começo

Clique → setTasks → React renderiza

Ao concluir uma tarefa, o estado muda. O React atualiza os componentes afetados pela nova informação.

Exemplo: marcar uma tarefa como concluída atualiza tanto o item quanto o contador de tarefas prontas.

É uma analogia ao Observer: não há um objeto observador clássico sendo cadastrado manualmente.

TasksContext.tsx · trecho real
const [tasks, setTasks] = useState([]);

const toggleTask = (id) => {
  setTasks(current =>
    current.map(task =>
      task.id === id
        ? { ...task,
            completed: !task.completed }
        : task
    )
  );
};
Padrão 03 · Provider

Compartilhar sem passar tudo por props.

O problema do prop drilling

Imagine passar tasks e toggleTask por cinco componentes que nem usam esses valores.

TasksProvider → TaskBoard → TaskCard

Com Context, TaskCard pode chamar useTasks() e acessar ações compartilhadas.

Context é útil, mas mudanças frequentes e grandes volumes de estado exigem desenho cuidadoso.

TasksContext.tsx + page.tsx
const TasksContext =
  createContext(null);

// Na página:
<TasksProvider>
  <TaskBoard />
</TasksProvider>

// Em qualquer descendente:
const { toggleTask } = useTasks();

Nem tudo são vantagens

Quando escolher. Quando simplificar.

Faz sentido

Produto com crescimento

  • Várias rotas e componentes compartilhados
  • Interface interativa e manutenção contínua
  • Necessidade de integrar servidor e UI
Exemplo: plataforma de cursos com catálogo, login e painel do aluno.
Pense duas vezes

Problema pequeno

  • Landing page quase estática
  • Complexidade que o time não precisa
  • Processamento pesado de CPU no servidor
Exemplo: página de evento de uma única seção pode funcionar muito bem só com HTML e CSS.
Vale lembrar

Não é React contra Next.js.

React sozinho

Liberdade para escolher roteador, bundler, estratégia de renderização e outras bibliotecas.

Ótimo quando você quer controlar cada escolha da stack.

React com Next.js

Convenções prontas para criar aplicações com rotas, layouts e componentes de servidor.

Ótimo quando a equipe se beneficia de uma estrutura compartilhada.

A melhor ferramenta é a que reduz a complexidade do problema, não a que adiciona mais recursos.
